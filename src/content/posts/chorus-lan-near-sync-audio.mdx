在多设备协同场景中，将 Mac 上的音频近乎无延迟、无相位撕裂地同步流式传输到多台 iOS 设备（iPhone / iPad）是一个看似简单但极具挑战的工程问题。本文记录在开发 Chorus 局域网近同步音频系统过程中的关键架构选型与踩坑经验。

## 一、场景：Mac 主机 + iPhone/iPad 从机

Chorus 的核心目标是构建一个低延迟、跨设备的局域网音频广播与协同播放系统：

- **Mac 主机（Host / Broadcaster）**：捕获系统音频输出或特定音频流，进行实时编码与分发。
- **iOS 从机（Receiver / Client）**：iPhone 与 iPad 作为扬声器节点接入，接收音频流并低延迟渲染。
- **应用场景**：【Ryan 补：如多房间同步广播、移动扬声器扩展、桌面协同听歌等个人体验与使用感受】

在局域网内，由于 Wi-Fi 抖动、设备处理延迟和系统时钟差异，简单的“发包即播”会导致明显的相位抵消（回声/空洞感）和累计时间漂移。

## 二、时钟：NTP/本地时钟漂移怎么量

音频同步的本质是时间基准统一。多台独立设备没有共享的硬件时钟，必须建立软件时钟同步层：

- **时钟同步机制**：采用简化版 NTP / PTP 往返时间测量算法，估算 Client 与 Host 之间的 Clock Offset 与 RTT。
- **漂移测量方式**：【Ryan 补：具体如何测量本地硬件时钟与主控时钟漂移、采样率微调方案与实现细节】
- **动态时钟调整**：通过微调音频播放速率（Audio Pitch/Rate Scaling）或丢帧/插采样点来平滑修正微小偏差，避免产生破音与爆音。

## 三、缓冲与起播对齐、断线重连

网络抖动与音频流畅度是一对天然矛盾，核心在于缓冲策略的设计：

- **环形缓冲区（Ring Buffer）**：客户端维护动态抖动缓冲区（Jitter Buffer），根据网络 RTT 与 Jitter 动态收缩与扩张目标水位。
- **起播对齐**：Host 下发带有预定呈现时间戳（Presentation Timestamp, PTS）的音频包，Client 提前缓冲并在绝对时间基准点统一触发播放。
- **断线重连与追帧**：当某台设备因弱网丢包或重连落后时，采用静音跳帧追赶策略快速对齐主时钟，保证群组播放一致性。

## 四、Windows Host 一笔带过

除了 Apple 生态内的 macOS 广播端，我们也探索了 Windows 端作为 Host 的可行性：

- **ChorusForWindows**：基于 WASAPI Loopback 捕获音频流，经由相同的网络协议分发给各 iOS/iPadOS 接收端。
- 目前已完成基础音频捕获与协议对齐，更多平台间差异与优化仍在迭代中。
